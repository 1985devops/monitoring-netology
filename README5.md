    ### Домашнее задание к занятию 17 «Инцидент-менеджмент» - Нугаев Алексей

## Задание

Составьте постмортем на основе реального сбоя системы GitHub в 2018 году.

Информацию о сбое можно изучить по ссылкам ниже:

* [краткое описание на русском языке](https://habr.com/ru/post/427301/);
* [развёрнутое описание на английском языке](https://github.blog/2018-10-30-oct21-post-incident-analysis/).


# Решение

Постмортем: сбой GitHub (11–12 ноября 2026)

Когда и сколько: 11.11.2026, 22:52 UTC — 12.11.2026, 23:03 UTC (24 ч 11 мин).
Критичность: высокая (статус Red).
Что затронуло: Issues, комментарии, вебхуки, GitHub Pages. Репозитории с кодом не пострадали.

В чём суть.
Из‑за 43‑секундного обрыва связи автоматика ошибочно переключила базу данных на другой регион. Возникла рассинхронизация (split‑brain): в двух дата‑центрах появились уникальные записи. Чтобы не потерять данные, инженеры вручную восстанавливали и сводили базы из бэкапов — это заняло почти сутки.

Хронология (ключевые точки).

21.10, 22:52 — обрыв связи, автоматическое переключение БД.
21.10, 22:54 — сработал мониторинг, началась диагностика.
21.10, 23:19 — отключены вебхуки и GitHub Pages для снижения нагрузки.
22.10, 00:41 — запущено восстановление из бэкапов.
22.10, 11:12 — главные БД возвращены в основной дата‑центр.
22.10, 16:24 — полная синхронизация баз, старт обработки накопившихся задач.
22.10, 23:03 — очереди разобраны, статус Green.

Что сработало, а что нет.
Хорошо: сохранили все данные пользователей, быстро заметили сбой и снизили нагрузку.
Плохо: автоматика не должна была переключать БД между регионами; прогнозы сроков восстановления оказались неточными; оповещения зависели от той же инфраструктуры, что и сервис.

Как предотвратят повторение.

Запретить автоматическое межрегиональное переключение БД без участия человека.
Сделать страницу статусов детальнее (показывать состояние отдельных функций).
Вынести блог и оповещения на независимые серверы.
Проводить регулярные учения с моделированием сбоев (Chaos Engineering).
